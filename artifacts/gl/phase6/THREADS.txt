1. WHAT IT IS
  Toggle: S31GL_THREADS, read once at the first general-path batch.
    0  one thread - the DEFAULT, unchanged pixels and code path (below)
    1  two threads: a pthread worker (Linux); falls back to 2 without one
    2  deferred: the worker's records run on the calling thread at each
       sync. The validation arm (a missing sync is a wrong frame every
       time, not a race) and, on the bare-metal RV32 counter, the exact
       per-thread instruction split
  Knobs (1 and 2): S31GL_TBAND rows per band (16), S31GL_TSPLIT k/n: the
  worker owns k of every n bands (1/2), S31GL_TRING ring kB (64),
  S31GL_TSPIN spin iterations before a futex sleep (4000), S31GL_TCHECK=1
  (every pipe copy scanned for an unrelocated pointer; diagnostic).
  Build knob for gates: -DS31GL_THREADS_DEFAULT=N (the suite passes no
  environment).

  Screen-space ownership, bit-identical by construction:
  - Every row belongs to one thread (own[y], banded). Only the general
    triangle filler (ztriangle_gen.c: every textured / blended / fused
    QuakeSpasm triangle, the world and alias fused fillers included) is
    split. Its set-up is done ONCE, by the application's thread (main):
    ztri_setup, the depth-epoch record (ztri_zepoch) and the dirty box
    (ztri_rows) - the only per-triangle code that writes shared state.
  - The rest (zpx_tri's texel level choice, the planes, the span loop) is
    fill_body. Both threads run ONE out-of-line banded copy of it
    (ZB_fillBodyGeneral / ...MT) for their own rows; spans are evaluated
    from plane equations at each span's first pixel (the edges step on
    through foreign rows exactly as before), so a pixel's inputs and
    instructions do not depend on which thread draws it or which rows the
    other one skips. Mode 0 keeps the unbanded body inlined, as before (a
    row test inside cost +0.3-0.5% on the replay).
  - A triangle that covers a worker row is queued (RecTri: its ZTri, the
    three ZVtxG, the flat colours: 340 B) in a single-producer
    single-consumer ring (release/acquire counters, futex sleep/wake with
    seq_cst fences on both sides). Main draws its rows at once; a triangle
    wholly in worker rows costs main only the set-up and the copy.
  - The stages read and WRITE the pipe (per-triangle texel stages placed in
    the slots, per-chunk filtered texels, lod_cur, the lazily built blend
    tables), so the worker has its own ZPipe / ZPipeX / ZBuffer view. Main
    queues a copy (RecPipe, 2.5 kB) whenever gl_build_pipe ran since the
    last one (pipe_serial) or after any sync; the worker relocates every
    pointer into the copied structures (p->x, p->zb, the texel slots, cur0 /
    cur1, tex / talpha into ftex / falpha, slot_col, zb->zmaxp; TCHECK
    found no other), and keeps its OWN world / blend tables (wtab, btab,
    satab: allocated by main at creation, rebuilt by the worker on a key
    mismatch - never malloc on the worker).
  - Not threaded (sync first, then every row on main): stencil batches and
    polygon stipple (their tables / patterns are not copied), buffers taller
    than 1024 rows, tier-1 batches (gl_update_raster syncs when a batch is
    not general), lines, points.
  - Sync points (S31T_SYNC: one load and branch when off, a drain when
    records are pending): glClear, lines, points, glBitmap, glDrawPixels,
    glCopyPixels, glReadPixels, glCopyTex*, glPolygonStipple, texture
    image / sub-image upload (texture.c, which also covers glCopyTex's
    upload), texture delete, glTexParameter, the depth-epoch rewrites
    (zep_materialise, zep_demote), a tier-1 batch, every tgl_ctx_* that
    binds or drops a buffer, make-current (the old context), the frame hook
    (gl_prepare_slow), glFlush / glFinish / glXSwapBuffers / glXWaitGL
    (s31gl_finish), s31gl_frame_end, context destroy (sync, quit record,
    join). The per-pixel order of writes is API order: one thread owns the
    pixel and drains its queue in order; the other thread's work on other
    pixels needs no order.
  Code: gl/tinygl/source/s31_thr.[ch] (new), ztriangle_gen.c (split),
  zpipe.h (ZPipe.thr), raster_sel.c, the sync sites; gl/api/context.c
  (s31gl_finish, glFlush / glFinish, s31gl_thr_stats); gl/bench/q_replay.c
  (per-frame qsrt lines, and a finish before each counted swap).

4. BOARD MODEL AND PREDICTION (an estimate, not a measurement)
  frame(threaded) = max( A + g * m ,  g * w / s ),  frame(one) = A + g = 1
    g  libGL's share of the application thread's frame (the rest, A = 1 - g,
       is QuakeSpasm itself and the present). NOT MEASURED on the board;
       the plan's "~60% libGL fill" puts g at 0.6-0.75.
    m, w  main's and the worker's libGL instructions as fractions of the
       one-thread libGL count (section 3), assuming time scales with
       instructions on each hart.
    s  the worker's speed relative to the application thread: the lent
       CPU gives Linux 0.82-0.84 of a core (docs/perf-review-2026-09-23.md),
       is ~15% slower per instruction (no PIE, its own 16 KB I-cache now
       filled from PSRAM, not flash, since libGL left XIP), and lvdesk
       takes ~30% of hart0 in games (docs/smp-finish-plan.md) - s = 0.5-0.7.
  Nearest (shipped default), 16 rows, windows 0-1 (W: the worker is the
  long pole):
                  g 0.6, s 0.5    g 0.7, s 0.6    g 0.75, s 0.7
    1/2           1.28-1.37x      1.34-1.46x      1.38-1.51x
    2/3           1.35-1.42x      1.44-1.46x      1.49-1.59x
    3/4           1.13-1.30x W    1.16-1.33x W    1.27-1.45x W
  Costs the model leaves out, each of which lowers it:
    - two-hart PSRAM streaming (assessment M1: never measured). Both
      harts share one 64 KB 2-way D-cache and one PSRAM bus; if the fill is
      bandwidth-bound the gain collapses towards 1.0-1.1x. The kill rule
      stands: M1 >= 1.4x two-hart store/copy before believing more.
    - the ring: 0.33-0.8 MB/frame written and read back (+ 30-38 pipe
      copies of 2.5 kB) - ~3-6 MB/s at 7-10 fps, a few % of PSRAM
      bandwidth; S31GL_TRING=16 keeps it cache-resident at the price of
      lock-step (ring-full waits, qsrt "full").
    - sync hand-offs: ~2 per frame. A sleeping cross-hart hand-off is
      300-500 us (worklog-2026-09-19); the worker spins S31GL_TSPIN
      iterations first, the main thread too, so at a sync the worker is
      usually awake. ~1 ms of a 135 ms frame at worst.
    - futex wakes when the worker idles between batches (not counted
      here: each is a syscall on a hart where syscalls are expensive).
    - lvdesk and the worker competing on CPU1 (present stalls).
  Prediction: QuakeSpasm timedemo 7.3-7.4 fps (SD-root library, nearest)
  -> 9-10.5 fps with S31GL_THREADS=1 S31GL_TSPLIT=2/3 if two-hart
  streaming scales; 7.5-8 fps if it does not. Worst case a regression
  from the sync / wake costs if the worker is starved on CPU1 - the A/B
  decides; the default stays 0.
  RAM: ~75 kB per threaded context (64 kB ring, 5.5 kB tables, 5.5 kB
  worker state) plus the worker's touched stack (64 kB reserved); 0 in
  mode 0.

6. BOARD A/B TO RUN (coordinator; stock QuakeSpasm 0.96.3 timedemo demo1,
   320x240, fullscreen AND windowed, fresh boot per arm, >= 3 runs per
   arm, quiet harness, the SD-root library of this tree - confirm by a
   string from this build, e.g. "libGL: S31GL_THREADS=" in its stderr)
  B0  S31GL_THREADS=0 (the default) vs the current library: must equal
      (mode 0 is the same code; +0.05% instructions).
  B1  S31GL_THREADS=0 vs S31GL_THREADS=1 (split 1/2, 16 rows): the headline.
  B2  S31GL_THREADS=1 S31GL_TSPLIT=2/3 (the nearest-filter balance) and
      3/5; pick by fps, watch the tail (long frames), not the median.
  B3  S31GL_TRING=16 vs 64 on the winner (cache residency vs lock-step).
  B4  PIE bounces during B1 (swt-arm.sh counter): must not rise (the
      worker's path is PIE-free by construction; a rise means a missed
      call - thrchk-pie.sh lists the candidates).
  B5  lvdesk present / A2DP / Wi-Fi sanity during B1 (the worker takes
      hart0 time from them), and per-process CPU (the worker thread shows
      as the client's second thread).
  B6  regression: glxgears windowed and fullscreen with S31GL_THREADS=1
      (tier-1 path: nothing is threaded; the worker is never created
      unless a general batch runs) and Doom / xcalc as usual.
  Before B1: M1 (two-hart memset/memcpy of 2 MB, libc-free workers,
  placement verified) is the cheap check of whether any of this can pay.

7. NEXT STEPS (not done in the time box)
  - Tier-1 fillers, lines and points stay single-threaded (glxgears gains
    nothing): the same set-up / body split applies to ztriangle.h.
  - Smaller records: only the ZVtxG fields the batch's planes read
    (ZPipe.need), and a pipe delta instead of 2.5 kB copies.
  - Dynamic balance: move the band split from the measured per-frame
    worker / main times (the counters exist in qsrt; on the board a
    CLOCK_THREAD_CPUTIME_ID pair per frame would do).
  - Stencil and stipple batches threaded (copy the 1 kB stencil table and
    the 128-byte pattern into the pipe record).
  - The worker could also take main's clears (G11's "second hart for
    clears"), if M1 says two-hart stores scale.

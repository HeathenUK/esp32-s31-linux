1. t8_l8_pass (target 2): WHOLE ALPHA BYTES
  The board profile (prof9) puts every one of t8_l8_pass's 97 samples in
  the TGL_AM_BITS loop: QuakeSpasm's lightmap blocks are RGBA with alpha 0
  in the unused area, so the L8 level carries a bit-per-texel alpha plane,
  and each texel read-modify-wrote its bit's byte (22 instructions a
  texel). The per-frame glTexSubImage2D of dynamic lightmaps is now: a
  head up to the next byte boundary as before, then 8 texels a step
  (unrolled) with the eight alpha bits built in a register
  (b = b << 1 | v >> 31, texels 7..0) and one byte store, then the tail as
  before; abad keeps the OR of the sums and is masked once (an OR has bits
  25-31 clear iff every word does). Same bytes, same alpha bits, same
  grey/opaque/binary statistics: l8eq.c (this directory) runs both loops
  on 2,000,000 random rows (width 0-129, any start bit, grey/colour,
  binary/any/opaque alpha): 0 mismatches.
    t8_l8_pass  274,683 -> 154,150 instructions a frame (-44%)
    proxy window 0 15.3397 -> 15.1006 (window 1: 14.0638 -> 14.0618 - its
    frames re-upload little)
  It cannot be a memcpy: the client sends RGBA words and the level stores
  one byte (grey) plus one bit (alpha) per texel; the statistics decide
  whether the texture stays L8.

2. zf8_wnn_t_p0s1 (target 1): PER-TRIANGLE STEPS HOISTED
  Board samples in the function (prof9, 1,611): pixels 70.4%, triangle and
  span set-up 15.1%, the 8-pixel block end (1/z, the steps, the jump-table
  dispatch) 14.5%. The span-start stalls are visible (49 and 64 samples on
  the two instructions after the first pixel's depth load and colour
  store: 7%), the rest is spread over the pixel's instructions at ~2-6
  samples each, i.e. instruction count. (board-prof9-zf8_wnn_t_p0s1.annot)
  qemu per instruction (zf8_wnn_t_p0s1-base.annot): 435 triangles, 9,483
  spans, 20,933 blocks, 93 k passing and 33 k failing pixels a frame; the
  pixel is 5 walk + 3 depth + 37 (pass) = 45, and every one of the 37 is
  needed for these bits (2 address calcs of 4-5 + load, the palette's 3
  byte loads, 3 x mul/sh1add/minu/srli, 2 shifts, 2 ors, 2 stores, the
  m = l 257, one spill). What was not needed: the span set-up recomputed
  8.0f x dfz/dsz/dtz/dsz1/dtz1 and reloaded the five steps from the ZSpan
  on every span. zf8_world_nn_b now takes the steps and their x8 as
  arguments; the triangle filler computes them once a triangle (the same
  multiply by a power of two, so the same values; zf8_world_nn_t, the
  per-span callers, compute them as before).
    span set-up 72 -> 60 instructions (triangle prologue 34 -> 45)
    zf8_wnn_t_p0s1 6,409,666 -> 6,299,206 a frame (-1.7%)
  Considered and not done, with the reason:
  - a lit palette (r 257 stored, saving m = l 257: 2 a pixel, ~190 k): a
    second 16-bit palette per P8 texture, i.e. new data in the D-cache and
    RAM on every world texture - tier 3's lesson.
  - SWAR products ((r | b << 16) x l is exact) - the per-channel rounding
    (x 514 + 32894, clamp, >> 19) then costs more than the multiply saved.
  - more work per span start (touching the next row) - S31GL_ZF8=2 was
    measured on the board and did not help; that arm is now removed.
  - 16-pixel perspective blocks - different bits.

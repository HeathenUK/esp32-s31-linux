2. WHAT CHANGED (gl/tinygl/source/zpipe_fused8.h; bit-identical)
  - Depth walked as z << 2: the 16-bit depth is one shift, no zext
    (bits 16-31 of 4z are bits 14-29 of z; 4(z + dz) = 4z + 4dz mod 2^32).
  - The depth test before any texel work (a failing pixel: 22 -> 8
    instructions).
  - The P8 texel's channels as three byte loads from its palette word (no
    field extraction: -3).
  - m = (l << sh) 257 as one multiply; for sh a constant, l * 257 with the
    shift folded into each channel's sh1add (the product's add).
  - One clamp constant for the three fields: min(31, v >> 19) =
    min(v, 2^24 - 1) >> 19 and min(63, v >> 18) = min(v, 2^24 - 1) >> 18.
  - A whole span per call: the batch's ZPipeX.run_mt is the filler's own
    runner (zf8_wnn_r_*), which cuts the span into the chunks zp_run_t
    would and advances the span values between them with zp_run_t's own
    statements (so the same fmadd rounding; the ZP_N_* conditions copied),
    so zp_run_mt_direct, its indirect call and a prologue per chunk go.
    The stage form (zf8_wnn_p0 ..., for any other caller of x->chunk) is
    the same body with N = f->n.
  - zf8_wnn_s_p0s1: QuakeSpasm's batch (P8, LEQUAL + write, sh 1 - its
    overbright) with sh constant and each 8-pixel block unrolled, entered
    at its first pixel through a jump table (a block of k pixels runs the
    last k copies, addressed back from the block's end): no pointer steps,
    no end test, no walk step after the last pixel. Two empty asm operands
    and the chunk end in a volatile stack slot keep GCC from holding
    derived pointers live through the pixels (each worth a spill a pixel).
    The other five variants (sh 0 / 2, LEQUAL no-write, LESS, RGB565) take
    the same body as a loop.
  - S31GL_ZF8 (s31_mtex.c, GLContext.zf8_on at the end of the struct): 1
    default; 0 the loop before this work for QuakeSpasm's batch
    (zf8_wnn0_p0 run by zp_run_mt_direct, byte-for-byte the old code: its
    7,793,557 instructions a frame reproduce exactly); 2 zf8 plus
    next-row touches (below). Both are board A/B arms.
  - ramtext.list: the new hot functions (S31GL_RAMTEXT=1 moves them and
    their .rodata jump table; the rv32 gate's ramtext line moved 69
    sections, 42,624 B, 0 read-only words left).

5. NOT DONE, AND WHY
  - PIE SIMD: not clearly worthwhile, so not attempted. The pixel is two
    gathers (index plane, palette, lightmap) PIE cannot do, and the
    products need 26 bits (x * l * 257 * 2 + 32894) where PIE has 16-bit
    lanes and no 32-bit lane multiply; moving eight pixels' r, g, b, l into
    lanes costs more than the 16 ALU instructions it would replace, and
    spans average 11 pixels (docs/tinygl-hw-accel-assessment-2026-09-25.md
    table rows PIE / G08; no compiler support, hand asm only).
  - A combined palette x light table (256 x 256 x 2 B = 128 kB) is twice
    the shared D-cache and RAM this board does not have; per-light rows
    built lazily cost a check a pixel. The exact product is already one
    multiply and a shNadd a channel.
  - The last spill (unit 0's shift, one lw a passing pixel, ~93 k a
    frame): all 27 allocatable registers are live; GCC never allocates ra.
    A local register variable in ra through asm operands would free one;
    ~1% of the filler, left for a hand-scheduled version if the board says
    the filler is still worth it.
  - The per-span prologue (71 a span, 0.67 M a frame): 12 saved registers
    and the batch's constants, once per 11-pixel span. The lever is a
    multi-span call from the triangle filler (GEOMETRY.txt section 5's
    plane-per-triangle idea), outside this function.
  - Hiding the depth / colour line misses: the samples say a store miss
    blocks the next memory access, so a prefetch probably only moves the
    wait. S31GL_ZF8=2 is there to measure it, not a recommendation.

1. LAZY PER-ROW CLEARS FOR ZB_fill16 (item 1): BUILT, MEASURED, REJECTED
  The instrument: gl/bench/qemu/cachesim.c + gl/bench/cachesim.sh (new): a
  QEMU plugin that runs every load and store of the counted frames through
  the S31 D-cache geometry (64 kB, 64-byte lines, 2-way, write-back,
  write-allocate with a fetch on a store miss - ASSUMED, docs/perf-ideas-
  sweep.md has only the geometry), LRU, and counts line refills and dirty
  write-backs - PSRAM traffic, 64 B each. One hart, no I-fetch, no other
  process: an A/B instrument for arms of ONE image, not a board number.
  (The root .gitignore's "qemu" also matches gl/bench/qemu/: cachesim.c is
  committed with git add -f; pcprof.c and memclass.c there never were.)
  Two builds, both bit-identical to the eager clear on all 84 full frames
  of p5f2-tf0 (hashes = the live capture), each with S31GL_LAZYCLR=0|1 in
  the same image:
  a) per row (the brief's design): a full clear of a retained buffer marks
     rows pending; zdb_grow / zdb_tri (every writer already reports its
     rows there for the dirty boxes; bact kept on while rows are pending,
     the fillers' dbc check narrowed to rows with none pending) write the
     pending rows a primitive can touch; tgl_ctx_sync (before a present),
     bind, make-current, depth release/bind, read/copy pixels, copy tex,
     the depth epochs' whole-buffer passes and masked/partial clears write
     the rest.
       instructions  15.3398 / 14.0639 -> 15.3609 / 14.0821 (+0.14%)
       PSRAM traffic 2,920.3 -> 2,880.9 kB a frame (-39 kB, -1.35%)
  b) per 32-pixel tile (one 64-byte line of either buffer; a bitmap word a
     row), each triangle writing only the tiles of its x extent:
       instructions  15.3398 / 14.0639 -> 15.7758 / 14.4029 (+2.8% / +2.4%:
                     zlz_rect 148 k, lz_tiles 137 k, extra ZB_fill16 calls
                     43 k a frame - nearly every triangle takes the slow
                     path, because a row is never whole until late)
       PSRAM traffic 2,920.3 -> 2,830.3 kB a frame (-90 kB, -3.1%)
  Why the merge does not happen: the eager clear's 4,800 lines (2 x 153.6
  kB) are one refill and one write-back each, and the idea was to save the
  render's second refill of the same line. Per row, QuakeSpasm's first big
  world triangles span tens of rows: a 50-row triangle writes 64 kB of
  colour and depth before its first span - the whole cache - so the lines
  are gone again when its spans reach them. Per tile, the triangle's bbox
  holds ~2x the pixels it covers, and the neighbouring tiles are evicted
  before the triangle that covers them comes; of 9,600 line transfers only
  ~1,400 are saved. At the tier-2 store rate (~95 MB/s) 90 kB is ~0.9 ms of
  a ~115 ms frame, and (b) costs ~430 k instructions (~3 ms at the board's
  ~130 M instructions/s): a net loss; (a) nets ~0.2%, unmeasurable. Not
  shipped; the tile version is kept as lazyclear/lazyclear-tiles.patch
  (611 lines, against 9ecf5f86) with its numbers.
  A lead the model turned up instead: the eager arms of two builds that
  differ only in unrelated code read 2,920 kB (the lazy build, LAZYCLR=0)
  and 3,261 kB (the base build) of PSRAM traffic a frame for the same loads
  and stores (+12%) - the heap, and so the colour / depth / texture
  addresses modulo the 32 kB way, moved. Same-set aliasing in the 2-way
  cache is worth more than the clears (cf. memory s31-write-combine-
  streams: offsetting CMA buffers 8-16 kB). On the board the colour
  buffer is the X server's SHM segment and depth the drawable's, so the
  replay's addresses say nothing about the board's; the lever would be a
  deliberate offset of the depth buffer against the colour buffer (a
  board A/B), not attempted.

2. WHAT CHANGED (bit-identical; S31GL_ZF8=4 restores tier 2 for all four,
   =3 the zf8 build; 0 and 2 keep their zf8 meanings with tier 3 on)
  a) zf1_blendt (zpipe_fused.c zf_ftab): zf1_blend is QuakeSpasm's flat
     view blend (C_FLAT, no texture, SRC_ALPHA / ONE_MINUS_SRC_ALPHA; 1,089
     chunks, 31,680 pixels a frame). Per destination field the result is a
     fixed field of PACK: t[dr] | t[64 + dg] | t[32 + db], each entry
     exactly PACK's own mask and shift of sr + MUL8(e(d), 255 - a) - the
     same btab expansions, so the same bits. 256 B built per flat colour
     and alpha (0.4 builds a frame), after btab's 192 B in the same block.
       per pixel 26.9 -> 19.0 instructions (mask test 3, three lookups,
       two ors, store, loop); per chunk 833.5 -> 579.7; frame 907,632 ->
       631,330 (-276,302); proxy 15.3397 / 14.0638 -> 14.9905 / 13.8368
  b) zf8_sbart (zpipe_fused8.h): the P8 status-bar blend (C_FLAT, texel,
     SRC_ALPHA / ONE_MINUS_SRC_ALPHA; 528 chunks, 15,360 pixels): the
     source half MUL8(t_c, fa) of each channel from a 256-byte MUL8(v, a)
     table (zf_bt8, its own alpha key bt8_a) instead of the multiply and
     div255 rounding.
       per pixel 48.9 -> 41.9; per chunk 1,465.5 -> 1,265.8; frame 773,760 ->
       668,352 (-105,408); proxy -> 14.8836 / 13.7299
  c) to_vg (raster.c): the general filler's vertex conversion computed the
     8.16 colours of every vertex; they are read only by the colour planes
     (ZP_N_RGBA) and the perspective-colour choice (ZPX_PC, which
     raster_sel.c sets only with them). gl_build_pipe records
     GLContext.vg_col; without it the four conversions are skipped.
       per vertex 58.0 -> 34.3 (5,247 a frame); frame 304,385 -> 179,980
       (-124,405); proxy -> 14.6926 / 13.6760 (after the bt8 key; the
       step measured 14.6910 / 13.6744 with bt8 in btab's rebuild)
  d) zf8_alias_blo (zpipe_fused8.h): the blended alias filler (the view
     model; 720 chunks, 4,300 pixels a frame, 105 instructions a pixel)
     stores a fragment of alpha 255 as PACK(r, g, b): MUL8(v, 255) is v and
     MUL8(d, 0) is 0 under both MUL8 definitions, so it is the blend's own
     result; any other alpha blends as before.
       every one of the frame's 4,300 blended alias pixels is opaque here:
       per pixel 105 -> 68; per chunk 836.1 -> 585.4; frame 602,345 ->
       421,732 (-180,613);
       proxy -> 14.5643 / 13.4431
  Total at the functions: -686,728 a frame; proxy -775,400 / -620,700 (the
  rest: fewer instructions of spill and call around them).
  The arms: S31GL_ZF8=4 reads 15.3690 / 14.0775 (tier 2 + 29 k, +0.19%:
  to_vg's vg_col test and the picks) with every hash identical; =3 reads
  15.9649 / 14.7529 (zf8 + 29 k).
  PSRAM traffic (the model, same image): T3 2,887.5 kB a frame, ZF8=4
  2,890.8 kB - the 512 B of tables cost nothing measurable.
  ramtext.list: NOT extended. Adding zf1_blendt / zf8_sbart / zf8_alias_blo
  makes the host (aarch64) link fail in ramtext.py ("site +0x52bc (adrp to
  s31_rt_len) does not reach its target"); the board build takes them
  (74 sections) but the host gate would not build. The board runs with
  S31GL_RAMTEXT_DEFAULT=0, so nothing changes by default; with
  S31GL_RAMTEXT=1 the tier-2 functions of the A/B arms are in RAM and the
  new ones are not (the arms would favour the old code).

5. NOT DONE, AND WHY
  - The triangle-level treatment for the one-unit fillers (item 2 as
    written): their batches are small triangles - 2,680 spans in 1,205
    triangles a frame, 2.2 spans each - so the per-span overhead the tier-2
    trick removes (zp_run's 60.7 a span, 163 k a frame, and the row loop's
    share of ZB_fillTriangleGeneral) is ~200-250 k a frame at most, while their cost was per pixel: the four changes above take
    ~690 k out of the same fillers' pixels instead. ZB_fillTriangleGeneral
    stays 610 instructions a triangle (~300 of set-up: the ST planes, the
    ZSpan initialisation, 12 saved registers); skipping the ZSpan fields no
    stage reads would save ~25 a triangle (~40 k) against the risk of a
    stage that does read one - not taken.
  - gl_vertex4f (905 k, 195 a vertex, flat): unchanged. Annotated per
    instruction (107 instructions on every vertex, 58 of viewport mapping
    on 79% of them) it is straight-line transform, clip code, viewport and
    copies; nothing left to fuse without restructuring glVertex.
  - The world filler (zf8_wnn_t_p0s1, 6.41 M, 44%): untouched here.
  - zx8_base_p8r (18 a texel) still writes idx[i] = i for its consumers;
    an identity index nobody writes would save 2-3 a texel (~50 k) but
    changes the ZFrag contract for every stage.

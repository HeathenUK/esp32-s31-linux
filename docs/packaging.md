# A package manager for this board

The goal is to stop the board being a fixed image: install something new
without rebuilding and rewriting the microSD.

## Why opkg

Buildroot offers exactly two package managers, `opkg` and `rpm`. There is no
`apk` and no `dpkg`. rpm brings a Berkeley-DB-class database and a large Python
tooling surface, which is the wrong shape for 15.4 MB of RAM. opkg is C, was
written for embedded targets, and its `.ipk` is just an `ar` archive containing
two `tar.gz` members - which matters a great deal here, because we have to
produce every package ourselves.

Cost on target: opkg plus `libarchive`. Both sit on the microSD, which has
106 GB free, and staged into XIP flash they would cost no RSS at all.

## The part that is not optional: there is no upstream feed

The usual answer - point the package manager at a distro mirror - cannot work.
This target is:

	riscv32, ilp32 ABI, -march=rv32imafbc_..._xespv2p2

Debian, Alpine, Fedora and OpenWrt are **riscv64 only**. Nobody ships a riscv32
binary feed, and even if they did, this build carries an Espressif vendor
extension. So every package in the feed has to come from our own Buildroot
output. That is a one-off piece of infrastructure, not a per-package chore, but
it has to exist before opkg is worth anything.

## Generating the feed

Buildroot already knows which file came from which package - it records that in
`$(O)/build/packages-file-list.txt` for its legal-info and graphing support.
Combined with `make show-info`, which emits JSON of every package with its
version and dependencies, that is everything a `.ipk` control file needs:

	packages-file-list.txt   package -> the files it installed
	make show-info (JSON)    package -> version, dependencies

so the generator is:

1. parse both, giving name, version, dependency list and file list per package
2. stage each package's files out of `$(O)/target`
3. write a `control` file - `Package`, `Version`, `Architecture`, `Depends`
4. `opkg-build` each staging directory into a `.ipk`
5. `opkg-make-index` over the result to produce `Packages.gz`

Steps 4 and 5 are host `opkg-utils`, which is why `BR2_PACKAGE_HOST_OPKG_UTILS`
is enabled alongside the target package.

This deliberately avoids `BR2_PER_PACKAGE_DIRECTORIES`. Per-package directories
would give the same information more directly, but turning them on changes the
build layout and forces a full rebuild from scratch, and `packages-file-list.txt`
is generated by the ordinary build already.

## Serving it

A `file:///` feed on the microSD is the default: it needs no network, survives a
Wi-Fi outage, and the card has the space. An HTTP feed served from the
development host over `wlan0` is the alternative when the feed is being
regenerated frequently, since it avoids recopying the card.

## The catch: the target filesystem is read-only where packages want to write

`/usr/bin`, `/usr/lib` and `/lib` are overlays stacking two cramfs XIP images
over the ext4 root:

	overlay /usr/bin overlay ro,lowerdir=/mnt/xip/usr/bin:/mnt/xip2/usr/bin:/mnt/sd-usr-bin

They are mounted **ro and have no upperdir**, so nothing can be written to them
at runtime and a plain `opkg install` fails with "Read-only file system" for any
package shipping a binary or a library. This is not a misconfiguration - it is
what makes userspace cost zero RSS, which is the single most valuable property
this board has.

The way in is a **non-recursive bind mount of `/`**, which exposes the ext4 root
without those overlays stacked on top. Packages install there, and the overlay
picks them up at the next boot because the ext4 root is its lowest lowerdir.
`/usr/sbin/s31-opkg` wraps this:

	mount --bind / /mnt/realroot
	opkg --offline-root /mnt/realroot "$@"

**An install therefore needs a reboot to become visible.** That is the price of
XIP userspace, and it is worth paying.

## Status: working end to end

	70 .ipk built from a 108-package Buildroot build
	index 17,666 bytes
	opkg 0.7.0 on the target, feed fetched over Wi-Fi

Proved against an empty root rather than by inference - installing `bc` into a
fresh directory delivered `/usr/bin/bc` and `/usr/bin/dc`, since installing over
an already-populated rootfs cannot distinguish "installed" from "was already
there".

Two gaps remain:

- **No dependency data.** `make show-info` did not return parseable JSON, so
  control files carry no `Depends:`. opkg installs happily without it but will
  not pull dependencies automatically.
- **The feed only contains what has already been built.** Adding genuinely new
  software still means enabling it in Buildroot and regenerating the feed. The
  win is that a *small* rootfs can ship while a *large* set of packages stays
  installable on demand - not that arbitrary upstream software appears.

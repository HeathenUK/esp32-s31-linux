# OpenGL on the S31: the end-to-end plan (2026-09-25)

This supersedes the staging in docs/tinygl-plan-2026-09-25.md. That doc's
goal and its xlite-style "our own library" pattern stand. Its SDL2 claim and
its budget are corrected here.

The engineering evidence behind this plan is in three places:
- docs/tinygl-hw-accel-assessment-2026-09-25.md: what the hardware can do
  and where TinyGL's time goes, 15 opportunities verified adversarially.
- The integration research, summarised in section 4 below. It covers SDL2
  2.32.10, SDL 1.2.15, freeglut 3.8.0, mesa-demos 9.0.0, xlite and xshim,
  with file:line references.
- The library survey (section 2): six implementations compiled for RV32 and
  instruction-counted on the same demos. Its files are in
  /tmp/claude-501/glsurvey/.
- The target-app survey (section 3): the GL calls of 20+ stock apps scanned
  against TinyGL's exports.

## 0. Rules this plan is held to

1. **Stock applications, unmodified.** glxgears, glquake and the rest run
   as their packages build them. No source change, relink, build define,
   custom library for one app, or per-app config or env steering (memory
   s31-never-rebuild-client-apps). Compatibility is the platform's job:
   libGL, GLX, GLU, xlite and xshim.
2. **Performance comes from the platform, which we own from the GL call
   down to the hardware.** That means:
   - the xshim MIT-SHM / XLITE-SHM approach extended to GL buffers;
   - a zero-copy present;
   - our DRM driver and the PPA.

   Platform code (libGL, GLU, GLX) may live in XIP flash, as xlite does,
   **and its hot code may be placed in RAM** (owner, 2026-09-25). This is
   the userspace counterpart of the kernel's `.text.fast`. App code stays
   on SD.
3. **Apps run from SD and are measured there.** No XIP, no tmpfs copies,
   no preload or mlock, and no arm that warms an app into RAM first (memory
   no-apps-in-flash).
4. **No regression elsewhere.** Every existing app keeps its current path
   and speed. Proof is a gate, not an argument.
5. House rules:
   - F without D, so `double` is a library call. It is banned on any
     per-vertex or per-pixel path.
   - Memory is the binding constraint.
   - Runtime toggles over rebuilds.
   - Fresh boot per arm, at least 5 runs, and the worst frame reported.
   - Each board test under 10 minutes.

## 1. Architecture

```
 stock app (SD) ── GL 1.x ──▶ libGL.so.1  (ours, XIP)
                               ├─ rasteriser core        (section 2)
                               ├─ GLX 1.4, client side   (section 4)
                               └─ present: MIT-SHM / XLITE-SHM / GEM (section 5)
                 ── GLU ────▶ libGLU.so.1 (SGI GLU from Buildroot's libglu, unmodified, XIP)
                 ── X11 ────▶ xlite (libX11) ──ring──▶ xshim in lvdesk ──▶ KMS / PPA
```

- **Packaging.** `buildroot-external/package/s31-libgl` is a Buildroot
  **`libgl` provider**: it sets `BR2_PACKAGE_HAS_LIBGL` and
  `BR2_PACKAGE_PROVIDES_LIBGL`, and installs `GL/gl.h`, `GL/glx.h`,
  `GL/glext.h`, `gl.pc` and `glx.pc`. This is what lets Buildroot build the
  stock GL packages (mesa3d-demos, libfreeglut, libglu, and later the games)
  against it. An `x11-stage` drop-in alone cannot do that. The library ships
  in the FIRST XIP image, as xlite does (memory s31-x11-libs-ship-path).
- **The soname is exactly Mesa's, `libGL.so.1`.** SDL and freeglut dlopen
  that name.
- **SDL builds are explicit** (section 4.2). Today both SDLs are built
  without GL. That stays until stage 5, and must never depend on build
  order. SDL 1.2's configure silently enables GL when `GL/gl.h`, `glx.h` and
  `glu.h` appear in staging, so `sdl.mk` gets an explicit switch.

## 2. The library

### 2.1 Choice: erysdren TinyGL as the base, grown by us

Every candidate was compiled for RV32 with the board's own flags and run on
the same demos under qemu with instruction counting. These are instruction
counts, not cycles: PSRAM stalls and the 16 KB XIP I-cache are not
modelled, and both punish big code further. Full report: the library
survey, whose files are in /tmp/claude-501/glsurvey/.

Millions of RV32 instructions per frame (soft-double calls per frame in
brackets):

| demo | **erysdren** | C-Chads | ScummVM TinyGL | Mesa 7.11 (OSMesa) | PortableGL |
|---|---|---|---|---|---|
| gears 320x240 | 3.51 [11k] | 2.93 [8k] | 5.10 [3.7k] | 3.17 [3.9k] | 62.3 [205k] |
| texobj 320x240 | **0.41** | 0.81 | 6.19 | 1.61 | - |
| texobj 640x400 | **1.27** | 2.53 | 20.49 | 5.20 | - |
| teapot 320x240 | 14.6 [53k] | 11.2 [38k] | **7.0** [14k] | 10.8 [24k] | - |

| | code (.text, -Os) | licence | fixed-function coverage | per-pixel cost |
|---|---|---|---|---|
| **erysdren TinyGL** | **36.6 kB** | MIT, active | GL 1.1 core; no blend, alpha test, fog, scissor, texenv | **cheapest** |
| C-Chads tinygl | 51.4 kB | MIT-style, archived | adds blend, depth mask, DrawPixels, glGetString | 2x on textured spans |
| ScummVM TinyGL | 1.92 MB (ztriangle alone is 1.65 MB) | **GPLv2+** | the richest: blend, alpha, depth func, stencil, fog, polygon offset, scissor, texenv, bilinear | 15x on texobj; 32-bit Z; a runtime format switch per pixel; `error()` aborts on stock apps' parameters |
| Mesa 7.11 classic | about 1.6 MB | MIT | complete GL 2.1 | 4x on textured spans; float fragments; 2,726 double sites; 8.9 MB of span arrays per context by default |
| PortableGL | 157 kB | MIT | GL 3 core, **no fixed function** | 18-38x TinyGL |

Also rejected:
- Modern Mesa: softpipe is many MB of code and RAM, and llvmpipe needs LLVM.
- SwiftShader: no RV32 JIT.
- gl4es: a GL-over-GLES translation layer, useful only as a compatibility
  reference.
- tinygles: dead.

**Decision.** Base on **erysdren TinyGL**. Its pixels are the cheapest
measured, it renders RGB565 natively, it is tiny (which matters because it
runs from XIP through a 16 KB I-cache), and it is MIT. Its weak spot is
geometry, and that weak spot is exactly the soft-double problem the
assessment's G01 removes. With that done, teapot is expected to fall below
ScummVM's 7.0 M.

How the other two contribute:
- **C-Chads**, MIT-style: its blending, glDepthMask, glDrawPixels and
  glRasterPos code is ported directly.
- **ScummVM**, GPLv2+: a **design reference only**. We read how it fits
  blend, alpha test, depth func, stencil, fog, polygon offset, scissor and
  texenv into a TinyGL rasteriser, then write our own. No code is copied,
  so libGL stays MIT.

**Fallback, only on evidence.** Mesa 7.11 classic, rebuilt with
`MAX_WIDTH` about 1024, if a target needs GL 1.3+ semantics TinyGL cannot
reasonably provide. Its price is 1.6 MB of flash, 2.7k double sites to
clean, and float fragments. Nothing in the target list (section 3) needs it
today.

### 2.2 What we add to TinyGL, and how it stays fast

The rules for the work:
- **Specialise, do not branch.** Each added test (blend, alpha, depth
  func, fog, texenv, scissor) is a state bit that selects a filler at
  triangle setup, never an `if` per pixel.
- Keep the number of fillers small: a handful of macro-generated
  variants, not ScummVM's 256. Code size is time from XIP (assessment 2.2).
- A frame that uses no new feature runs today's filler, byte for byte, and
  a gate proves it (section 6, stage 3).

The work, in the order the targets force it (feature matrix in section 3):

| # | feature | forced by | notes |
|---|---|---|---|

## 2.3 GLU

GLU is Buildroot's **libglu 9.0.3 (Mesa GLU, SGI-B-2.0), unmodified**,
built against our `gl.pc`, and shipped in XIP as a platform library.
- It is needed by rRootage, Chromium B.S.U., SDL-Ball, the GLUT demos and
  xscreensaver.
- It is not needed by glxgears, the xdemos, testgl2, GLtron or TyrQuake.
- TinyGL's own glu.c (8 functions) is dropped.
- Cost to measure: libGLU's NURBS part is C++ and pulls in libstdc++ for
  every GLU app. Meson has no option to drop NURBS, and we do not patch it.
  Record the resident cost, meaning libstdc++'s data pages, on the first
  GLU app.

## 4. GLX, SDL and the regression guard

### 4.1 The GLX surface (client side only)

- **Exported for real:** `glXGetProcAddressARB` and `glXGetProcAddress`,
  which must also return GLX functions, because SDL2 fetches all of GLX
  through them (SDL_x11opengl.c:281-284). Also `glXQueryExtension`, which
  must tolerate NULL arguments (freeglut, fg_init_x11.c:181).
- **GLX 1.4, the whole API:**
  - ChooseVisual, GetConfig, CreateContext / CreateNewContext,
    DestroyContext, MakeCurrent / MakeContextCurrent, SwapBuffers;
  - IsDirect (always True), GetCurrentContext / Drawable / Display;
  - QueryExtensionsString, QueryServerString, GetClientString, QueryVersion
    (1.4);
  - ChooseFBConfig, GetFBConfigs, GetFBConfigAttrib (the full table),
    GetVisualFromFBConfig, QueryDrawable.
- **The GLX extension string** is `GLX_ARB_get_proc_address
  GLX_EXT_visual_rating GLX_EXT_swap_control GLX_MESA_swap_control
  GLX_SGI_swap_control`.
  - GLX_ARB_create_context is **not** advertised: nothing here is GL 3, and
    SDL then takes its legacy path cleanly.
  - Not advertised either: multisample, sRGB or ES profiles.
- **`glXGetProcAddress` returns NULL for anything unimplemented.** Mesa's
  stub-for-any-name behaviour is the thing not to copy, because a stub makes
  SDL believe a function exists.
- **Visuals.** Only xshim's 0x21 (RGB565 TrueColor):
  - It serves both single- and double-buffered requests, as Mesa's Xlib
    driver does.
  - It reports depth 16, stencil 0, accum 0, caveat SLOW.
  - DirectColor requests return NULL, so SDL 1.2 retries with TrueColor
    (SDL_x11gl.c:198-212).
  - Stencil or accumulation requests fail honestly.
- **xlite needs nothing new.**
- **xshim** optionally answers "GLX" as a present extension with
  GLXQueryVersion, and BadRequest for everything else, so a foreign indirect
  libGL fails cleanly. No client here asks the server.
- **Always:**
  - libGL allocates colour and depth lazily, at the first clear or draw, not
    at MakeCurrent.
  - It logs one line per context created, with pid and comm, so a gate can
    prove which processes made one.

### 4.2 SDL: the decision and the guard

**Today.** SDL2 2.32.10 has `SDL_VIDEO_OPENGL`, `_GLX` and `_RENDER_OGL`
undefined (config.log:7). SDL 1.2.15 is the same. So adding libGL changes
**no** existing app, by construction.

**If SDL2 is built with GL naively, three things go wrong at once:**
- `SDL_CreateRenderer(-1, …)` tries "opengl" before "software"
  (SDL_render.c:100-137).
- **Every** SDL2 window surface becomes a GL streaming texture, including
  apps that ask for the software renderer. The texture-framebuffer probe has
  no default-off on X11 (SDL_video.c:2667-2705, 268-283).
- The GL renderer recreates the X window before checking anything
  (SDL_render_gl.c:1717-1729).

chocolate-doom and every textscreen tool would change path.

**The design:**

| SDL | stages 0-4 | stage 5 (SDL GL apps) |
|---|---|---|
| SDL 1.2 | GL off, stated explicitly in `sdl.mk` | GL on. Safe: only `SDL_OPENGL` modes pick a GL visual (SDL_x11video.c:928-936). prboom and prboom-plus are `--disable-gl`, and OpenTyrian is a SWSURFACE app. |
| SDL2 | GL off | **GL contexts on, SDL's own GL render driver off.** A post-configure hook undefines `SDL_VIDEO_RENDER_OGL`, so "opengl" is never in the renderer list, and the window-surface probe finds no accelerated driver and keeps today's X11/MIT-SHM path. It is honest: GL is fully there for apps that ask for it; only SDL's 2D-over-GL renderer is absent. It is recorded next to `sdl2.mk`. |

**The owner's constraint (2026-09-25).** Nothing here may reduce existing
performance. SDL2 is already slower than SDL 1.2, and SDL apps that use our
GL must still be possible. How the design meets that:
- **SDL 1.2 GL comes first** (early in stage 5). It is safe by construction,
  and many classic GL games are SDL 1.2.
- **SDL2 GL comes after it, as a separate step,** and is shipped only if
  the regression gate below shows the SDL2 set identical on every count:
  - zero GL contexts;
  - no extra CreateWindow;
  - fps and CPU inside the shipped spread.

  It is reversible with one Buildroot switch: back to
  `--disable-video-opengl`.
- **Why "identical" is expected, not hoped for.** Without
  `SDL_VIDEO_RENDER_OGL`, an app that does not set `SDL_WINDOW_OPENGL` runs
  the same code paths as today:
  - the renderer list is unchanged;
  - the texture-framebuffer probe finds no accelerated driver;
  - `X11_CreateWindow` takes the non-GL visual branch;
  - GL is loaded only for an OPENGL window.

  The gate is the proof.

Belt and braces, in libGL:
- `GL_RENDERER` is exactly `"Software Rasterizer"`. That is literally true,
  and it is SDL's own sentinel for declining the texture framebuffer
  (SDL_render_gl.c:1693).
- GL_VERSION is reported honestly.
- `glBlendEquation` and `glBlendFuncSeparate` are not exported until the
  SDL2 gate has been re-run with them.

Rejected ways to prevent the switch:
- A small GL_MAX_TEXTURE_SIZE: it turns a fallback into a crash.
- Caller heuristics: dishonest.
- `SDL_RENDER_DRIVER` or `SDL_FRAMEBUFFER_ACCELERATION` in the environment:
  env steering, which breaks rule 1.

**The regression gate (every stage that ships a library):**
- chocolate-doom windowed and fullscreen, one textscreen or setup tool,
  prboom, OpenTyrian, TyrQuake-x11, xcalc, st and xfiles.
- Each must create **zero** GL contexts (from the libGL log line).
- Each must create no extra X windows (from xshim's CreateWindow count).
- Each must run at unchanged fps and CPU against the already-measured
  shipped spread (memory targeted-testing: compare with the recorded spread
  rather than re-measuring the old build).

## 5. The present path: where our control of the stack pays

The order is correctness first, then removing copies. Each lever is A/B'd
with the assessment's kill rules, and a present lever must never lower fps,
whatever CPU it saves.

**P1, stage 1: MIT-SHM.**
- libGL's colour buffer is a MIT-SHM segment at 16 bpp, and the rasteriser
  renders straight into it (`ZB_open` on that memory, no copy inside the
  library).
- `glXSwapBuffers` is `XShmPutImage` with send_event. The next frame's
  first write waits for ShmCompletion.
- In fullscreen, xshim's scanout alias makes that one copy the present
  (measured on SDL: lvdesk 4.9-6.1 ms per present against 8.5-9.2 ms
  without it, xshim.c:1596-1604).
- Windowed it is two copies (the shim copy plus the LVGL blit).
- This gives correct back-buffer semantics.
- Swap interval: 0 means no wait; 1 means wait for completion, which is
  vblank-quantised at about 42 Hz (memory s31-repaint-vblank-quantised).

**Not taken: rendering into the XLITE-SHM window memfd.** It is
front-buffer rendering, which tears windowed, and `px_shared` disables the
fullscreen alias (xshim.c:1647-1652). It saves one windowed copy at the
cost of correctness.

**P2 (assessment G05 + G06): zero-copy fullscreen, the real prize.**
- A new XLITE-SHM request re-homes a fullscreen GL window as a 16-bpp GEM
  dumb buffer (a bpp-2 variant of `win8_gem_alloc`, xshim.c:1269) and hands
  back a dma-buf through the existing PRIME path (xshim.c:9347-9380).
- lvdesk ADDFBs that GEM handle as the mode framebuffer instead of creating
  its own (kms.c:662-745), and libGL renders straight into what is scanned
  out. There is no copy at all.
- **A consumed fence** in a spare `xring_hdr` word: lvdesk publishes
  `consumed=seq` when the PPA scale, or the windowed blit, has read the
  frame. libGL waits on it before the next frame's first write.
- Double-buffering costs a second CMA buffer. Measure CmaFree under a GL
  client first, stay at 320x240 and 320x200 until then, and fall back to P1
  whenever the allocation fails.
- Gate first: M2, whether the "3-stream 18x" is cache-set aliasing, before
  any GL buffer goes into CMA.

**P3 (G06 + G15, one patch to our own DRM driver):**
- PPA clear-at-swap: a fill ioctl chained after the scale, so the colour
  clear costs the CPU nothing.
- `PRESENT` extended to the mode framebuffer: writeback plus scale with no
  atomic commit, replacing about 2.2 ms of DIRTYFB per 320x200 frame
  (kms.c:421).
- Both sit behind module parameters. Confirm the flash with `uname #N`, then
  regression-check Doom, Quake and the desktop.

**P4 (G07):** damage from the rasteriser's bounding box, so windowed
presents copy only what changed, not a row-hashed full frame.

**Render-small-and-scale (G04)** is for panel-size fullscreen, the only
case that does not fit in RAM at native resolution:
- It renders at 400x240 and lets the PPA scale it (0.6 ms of CPU against
  17 ms).
- It needs an xshim request for "buffer smaller than geometry" and viewport
  mapping in libGL.
- It is a visible quality policy. **The owner chose ON by default**
  (section 7). It stays a toggle, and its fps is never quoted as
  like-for-like.

## 6. Stages, gates and kill rules

Each stage ends with a board-verified result that is shipped and committed.
Every performance claim follows the house measurement rules: fresh boot per
arm, 5 or more runs, discard the first, report the spread and the worst
frame. **Correctness** is judged against ground truth: the same stock app
run under Xvfb and Mesa on the host at the same size, compared by pixel
runs with a tolerance (memory s31-xvfb-ground-truth).

| stage | deliverable | pass rule | kill / fallback rule |
|---|---|---|---|

### 6.2a M2 settled (MEASURED, 2026-09-25, rootfs/m2bench.c)

The "3-stream 18x on dumb buffers" is **cache-set aliasing, not
write-combine**. The three stock dumb-buffer mappings took 238-294 ms for a
400x300 three-stream pass. The *same* mappings, with two pointers offset by
16 KB and 8 KB, took 9.4-14 ms, against 7.9-11.8 ms on the heap.

So GL buffers **may live in CMA** (P2: render straight into the scanned-out
GEM buffer; PPA-reachable colour and depth), **provided buffers that are
streamed together are allocated at staggered offsets**. The colour and
depth planes of one context, and the texture being sampled, must not be
congruent modulo the 32 KB way size. libGL does this stagger itself when it
carves its buffers.

### 9.2 G04 render scale: ON by default for panel-size fullscreen

**Mechanism.**
- libGL (gl/glx/glx_present.c) asks the server once per buffer allocation,
  with the private XLITE-SHM request RenderScale (minor 3). The request is
  discovered through the extension name "XLITE-RSCALE", so an older xshim
  is never sent it.
- xshim (lvdesk/xshim.c, `rscale_request`) grants it only for the client's
  own depth-16 top-level that is exactly the panel size and is fullscreen
  or asking to be.
- libGL's colour and depth buffers are then 400x240. The whole-frame
  ShmPutImage lands in a server-private 400x240 surface, and the desktop
  scans that out as a 400x240 mode (`fsnat_cb(2)`), which the PPA scales
  2x.
- The window stays 800x480 in every reply and event, and pointer events
  arrive in 800x480 space.
- **Fullscreen only (owner's review, 2026-09-26).** A panel-size window
  that is not fullscreen is refused and renders natively
  (artifacts/gl/present/g04-panelsize-windowed-native.jpg).
  g04-panelsize-windowed-upscaled.jpg shows the earlier, unapproved
  behaviour.
- **Revocation.** A window that LEAVES fullscreen has its grant revoked.
  - xshim writes 1 into a spare word past the image in the client's
    segments (`rs_revoke`).
  - libGL reads that word at every present (`glxi_surf_revoked`), which
    needs no round trip and works even when the app eats every event.
  - libGL then puts the frame already drawn and remakes its buffers at
    native size before the next frame.
  - Tested with a client that leaves EWMH fullscreen at the same 800x480
    size: xshim logged `not live`, `dropped`, then `refused`; libGL
    logged `buffers 400x240` then `buffers 800x480`.
- Fallbacks:
  - The 2x CPU expansion into the window's own pixels covers only the
    frames already in flight when the scale stops being live.
  - If the desktop cannot scan the surface out, it calls
    `xshim_fsnative_refused()` and the window is presented from its own
    pixels. This was tested with LVDESK_NOFULLSCREEN=1:
    artifacts/gl/present/g04-refused-fallback.jpg.
- Toggles: `XSHIM_RENDERSCALE=0` (server) and `S31GL_RENDER_SCALE=0`
  (libGL).

**The core half is NOT in the shipped libGL yet.** It is the new core
entry point `s31gl_set_render_scale()`, which maps viewport, scissor, raster
position, the pixel paths, and line and point widths, and makes glGet
report the application's values.
- gl/tinygl and gl/api belong to the concurrent host workflow, so the core
  change is a patch against HEAD: artifacts/gl/present/g04-core.patch, with
  gl/tests/rscale_test.c.
- It applies to today's working tree with 2 hunks to merge by hand
  (clear.c and one hunk of s31_draw.c).
- gl/glx references the entry point WEAK. The shipped tree builds and runs
  without it: glxi_core_can_scale() is 0 and libGL never asks.
- Merge the patch and rebuild s31-libgl, and G04 is on.
- Host check (s31-glref, rscale_test): the same scene at 800x480 native and
  at render scale 1. The two differ in 1 of 96,000 buffer pixels and 4 of
  384,000 read-back pixels, against the 2x2 block rule. glGet VIEWPORT,
  SCISSOR_BOX, LINE_WIDTH and CURRENT_RASTER_POSITION are identical.

**Board (test libGL at /root/g04, built from HEAD core + patch + gl/glx).**
glxgears -fullscreen, 1 SHM buffer. Not like-for-like: the scaled arm draws
a quarter of the pixels.

| arm | fps (runs 2-6) | median | glxgears CPU | lvdesk CPU | present gaps 100-200 / 200-400 ms per 10 s |

| native 800x480 (`S31GL_RENDER_SCALE=0`) | 10.4-11.5 | 10.5 | 63-68% | 35-37% | 10-24 / 1-4 |

### 9.3 SHMBUFS=2: no spin; two buffers by default up to 200 kB

**The suspected spin is not one.** With glxgears pinned to CPU0 and 2
buffers, the h1s sampler put 80% of the samples in the rasteriser:
- memset_16 24.5%;
- ZB_fillTriangleFlat_lt 19.9%;
- glopVertex 8.2%.

No xlite or GLX wait symbol is in the top 30, and the kernel is idle 4.4% of
the time. The "98% of a core" is the client no longer idling while the

| arm | fps (runs 2-6) | median | glxgears | lvdesk |
|---|---|---|---|---|
| windowed 300x300, 1 buf | 28.6-30.4 | 28.9 | 60-63% | 50-52% |

### 9.5 Windowed zero-copy ("segment hold"): built, measured, rejected

**What was built.**
- XLITE-SHM minor 4 HoldSegments, discovered as "XLITE-HOLD".
- A client ping-ponging two segments lets the window SHOW the segment
  until its next put, and that put's handling sends the completion.
- There is no copy per frame, and the window's own buffer is freed.
- libGL waits serially: a buffer is free once the put AFTER its own has
  been processed. A buffer not followed by a put is withdrawn, not waited
  on.

**It is correct.** A one-colour-per-frame test client was recorded with
mjpegrec under pointer, popover and move traffic:
- 0 torn frames in each of four recordings (117-169 frames);
- the unpaced control (S31GL_NOWAIT) tore 1-29 frames, which shows the
  checker can see tears.

**It saved the copy but LOWERED fps.** Windowed glxgears 300x300, 2
buffers, fresh boot per arm, runs 2-6:

| arm | fps | median | glxgears CPU | lvdesk CPU |
|---|---|---|---|---|
| copy | 37.6-40.3 | 37.9 | 87-98% | 69-72% |
| hold | 31.9-35.7 | 32.6 | 70-79% | 43-46% |

- The cause: a segment is freed only by the NEXT put, so the client waits
  a round of the server's loop before every frame.
- By the plan's rule a present lever never lowers fps, so the lever is
  reverted.
- The reasoning and numbers are recorded at "REJECTED 2026-09-26" in
  xshim.c mitshm_request. The patch is in artifacts/gl/present/hold/.
- Untried: a third segment would remove the wait, at +180 kB.

A zero-copy CEILING measurement (a desktop that skips the copy and shows
wrong pixels) gave 38.9-48.5 fps against 35.2-41.3 on its own binary. That
is the most any copy removal can give here.

## Status, 2026-09-26 evening: the glxgears fullscreen dips (task 1) - found, fixed platform-side, shipped

Full account, data and instruments: artifacts/gl/dips/README.md.
- **Cause: PIE traps on the lent CPU.** musl's libc.so uses PIE (hart 1's
  SIMD) in strcmp, memcmp, memchr, memrchr and **memcpy from 64 bytes up**
  (the "exactly four functions" note missed memcpy). Linux CPU1 is hart 0,
  lent by FreeRTOS, with no PIE. A task that reaches one there traps and is
  moved to CPU0. When that is the desktop, it lands on the fullscreen
  client's CPU and the pair ping-pongs for 0.5-3 s (the client's libGL
  glBegin has a 64-byte memcpy + memcmp, ~4 a frame, that can trap too).
  Long frames: 8-12 involuntary switches each instead of 0.2-1.3, and
  0.86-1.18 PIE bounces each against 0.000-0.005 per normal frame. Found with
  rootfs/swapstamp.so (per-swap client timing) and a diagnostic kernel #394
  (patches/0072, esp32s31_pie_log; not shipped, the board runs #393).
- **Most of the measured 50-100 ms clusters were the harness.** busybox sh
  is a PIE user: shell loops, cpushare.sh and runsh polls on the lent CPU
  bounced (259 of one window's 368 bounces), and lvdesk's own per-long-frame
  /proc/vmstat strstr fed back. Quiet harness (gears-swt.sh): 0-1 frames of
  50 ms or more per 35 s window in every arm.
- **Fix, shipped (lvdesk e83b9d67, XIP):** lvdesk/lentcpu.c defines the PIE
  string/copy functions in the executable and dispatches on the thread's
  rseq cpu_id: libc's PIE routine on CPU0, a scalar loop elsewhere. The
  periodic paths no longer use libc entry points that reach PIE internally.
  Fresh boots: PIE bounces per window 6-22 -> 1-8; windowed fast-present
  49-52 -> 51-54 fps (no regression). Fullscreen fps stays bimodal by
  placement (~40 fps with glxgears on the lent CPU, ~47 on CPU0) in every
  arm.
- **Regression:** gate2 PASS, x11-compat-gate PASS, prboom fullscreen 44.2 and
  windowed 48.2, sdlquake 20.1.
- **For the library round:** LIBGL-OPPORTUNITIES O7. Replace glBegin's
  modelview-cache memcpy + memcmp (vertex.c:203-205) with a 16-word loop, or
  use the same rseq dispatch for large copies.

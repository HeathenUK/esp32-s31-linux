- **lvdesk crash on client exit - FOUND AND FIXED** (`lvdesk/xshim.c`
  px_release / xshim_window_pixels). A window aliased to its background pixmap
  (xfiles) that is then RESIZED kept its old-size RGB565 shadow because the
  alias early-return in px_release skipped freeing it; the next conversion wrote
  the larger frame 143 KB past the end (zeros for black), smashing musl slot
  headers (lvdesk died in free() at the client's exit, exit 139) and neighbouring
  windows' pixel mappings (the "xfiles over xcalc corrupts xcalc" report). Fix:
  derived buffers are freed on every px_release path and the shadow carries
  its allocated size (`shadow_n`) and is reallocated if too small. Verified: 4
  rounds with the header watch + 6 production rounds on one instance, where
  every earlier run died by round 4.
- **Second lvdesk crash - FOUND AND FIXED** (`lvdesk/xshim.c` DestroyWindow).
  A client that sends DestroyWindow and then exits (SDL2: SDL_DestroyWindow,
  SDL_Quit) had its pixels freed/munmapped by a bare res_free() while lvdesk's
  LVGL image still pointed at them; the desktop only learned of the window at
  socket close. Any refresh in the gap read unmapped memory (lv_memcpy SIGSEGV
  at the buffer address). Now DestroyWindow calls close_cb (xwin_on_close: forget
  the window, leave fullscreen if it owned it, do NOT drop the client) before
  freeing, and frees the subtree as X does. Found by the new `xwin_dsc_check()`
  (XSHIM_CANARY): "STALE IMAGE ... shim now 0" at the loop checkpoint, one line
  after `res_free 0x200002` following `[240] DestroyWindow`. This is the
  "desktop absent after the SDL2 run (exit 90)" from the 2026-09-13 benchmarks.

  hcd_port_handle_event -> xSemaphoreGive). Starting it 3 s after release
  boots clean. Cause of the interaction NOT yet established.
- FOUND 2: with the host up, the hub attaches at HIGH speed and esp-usb's hub

  applied: force the root port to full speed (HCFG.FSLSSupp, the HAL has
  usb_dwc_ll_hcfg_set_fsls_supp_only) so the hub is a FS hub and needs no TT.

- RESOLVED (20:10): FOUND 2's fix (root port pinned to full speed via

## Doom audio fixed (2026-09-19 20:30) - the hiss and "bottom of a well"

Not the mixer, not s31route, not the loader: the ES8389 never matched a
clock row at 11025 Hz. dmesg said so on every Doom launch ("Clock
coefficients do not match") and an I2C dump during the stream showed the
clock dividers (0x04-0x0A) still at their idle values. The 11025 row from
patches/0042 assumed MCLK = 256 x rate; this board has no MCLK line and with
dac_ref=Y the driver derives the clock as width x rate x 4 = 64 x rate. Rows
{64, 705600, 11025} and {64, 1411200, 22050} (cloned from the 44100 64x row)
match; 32x rows added too for dac_ref=N. Kernel #226. Verified: dmesg clean,
dividers programmed (0x05=0x51), and by ear ("Audio sounds good").
The one earlier "perfect" run remains unexplained and was probably at a
different rate. Windowed timedemo with sound is in the low teens of fps; that
is the A/B's job, not an audio fault.

## 2026-09-20 morning: three dip levers built

User: "Why are we using X sockets at all?" - both ends are ours. Built:

1. **XLITE-RING** (xlite/xring.h, xlite/*.c, lvdesk/xshim.c): the X byte
   stream in a per-connection memfd (64 KB c2s + 32 KB s2c SPSC rings) with
   one O_NONBLOCK eventfd per direction as doorbell. Negotiated by
   QueryExtension("XLITE-RING") + Attach; the reply carries 3 fds on the
   socket; the socket then only carries SCM_RIGHTS (1-byte dummy; the ring
   reply says so with detail 0xFD) and its HUP. XConnectionNumber() returns
   the s2c eventfd so SDL's select() still works. XLITE_RING=0 /
   XSHIM_RING=0 turn it off. Doorbell rule: writer sets sig THEN writes the
   eventfd, and skips both if sig is already up; reader clears sig and
   drains the eventfd BEFORE looking at the ring. First boot: prboom's two
   connections attached and rendered at once.

**Step 3 answered (rootfs/pieprobe.c, #303):** a running wget got 2 s of CPU in
7.5 s confined to CPU1 with ZERO PIE traps; idle lvdesk 1 trap in 7.5 s. Yet
every process had affinity {0}: the boot shell traps once at ~6 s, is pinned,
and fork() inherits the mask. The permanent pin, not PIE, emptied CPU1.
-> `esp32s31_pie_bounce=N` (patches/0056): migrate on a trap, restore the mask
at once, pin only a task trapping > N/s. `make linux SMP=1 PIE_BOUNCE=20`.

**That exposed the real bug.** #305 (bounce from boot) stalled on every boot -
the same signature as the unanalysed #300 record. Built a hart0 POST-MORTEM
(bootloader/main/s31_vcpu.c: hart 1 PC/SP via the bus monitor, both stacks and
kernel arrays read out of PSRAM, hart 1's CLIC via the alias;
scripts/board/pm-resolve.py resolves it; `conlog.py <out> <s> 115200` reads the
loader black box). What it showed, boot after boot:
  - CPU1: mprotect/fork -> flush_tlb_mm -> smp_call_function_many_cond,
    holding a page-table lock, waiting for hart 1's IPI ack;
  - hart 1: reclaim/compaction -> page_vma_mapped_walk -> spin_lock on that
    lock - or circling the idle loop - with timer, IPI (FROM_CPU_1 = 1) and
    device interrupts pending AND enabled, threshold 0, never taken;
  - the kernel's own reading from the idle loop: sintstatus = 0x0000ff00;
  - first bad context switch always with scause = timer or IPI interrupt.
The CLIC raises the hart's level on every interrupt and only an xret lowers
it; Linux schedules from irqentry_exit() before that sret. Full account and
the three measured traps on the way (scause=0 does nothing; scause aliases
SPP/SPIE; entry.S is too late) in patches/0057-esp32s31-clic-level-drop.
#313: boots, 47,530 drops all effective, 0 of 22,361 switches at a raised
level, 924 PIE bounces, nobody pinned, user time CPU0 836 / CPU1 640 ticks.
#314 = the same without the probes. Wrong turns, for the record: my first
drop was in entry.S after `call do_irq` (schedule had already happened); an
OpenSBI MPIL mask for M-mode interrupts changed nothing and is reverted.

This is also a UP latency bug (kthreads woken from an interrupt run deaf to
the tick and all devices until the preempted task srets) - likely behind
"dw_mmc: Unexpected interrupt latency". Build a UP kernel with the fix and
re-measure the baseline before comparing anything to it.

# Performance plan, 2026-09-23

The order of work drawn from `perf-review-2026-09-23.md` (183 proposals, three
lenses each), after a second review of that report's own recommendations.
Read the review for the evidence; this file is the plan and its running log.

## What the review established

- No remaining lever is of SMP / RAM-text / X11-flattening magnitude. Of 95
  reviewed candidates, zero rated large; of 88 discovered, one rated medium
  (the CPU PLL overclock, weak on its other two lenses).
- What remains is 1-4% items, most individually smaller than the per-boot
  lottery (+-10% on Quake, ~17% on the desktop). They cannot be validated one
  at a time on fps.
- Quake at 320x240 with sound (48 kHz, the rate it asks for - HARD RULE
  2026-09-23, see log) lands at **17.5-18.2 fps** with everything
  shipped, **18.2-18.7** at 360 MHz, **18.8-19.7** only at a stable 400 MHz.
  20 fps is not reliably reachable without the overclock or a rule change.

## Where this plan departs from the report's order

1. **The per-boot lottery is the largest known effect** (10-17%) and is what
   makes every other item unmeasurable. The cache counters (T1.5) are the
   instrument that the earlier chase never had. Point them at a slow boot
   before anything else; if nothing shows, close it and design around it.
2. **C45 (the 7-8 ms kworker hand-off) is Tier 1, not a footnote.** That
   constant forbids moving lvdesk's 3.6 ms expand-and-present per frame off
   CPU0 onto the 64%-idle CPU1: ~6% of CPU0 at 16 fps, larger than C39. The
   CLIC-level bug that plausibly caused it was fixed (patches/0057). One
   same-boot A/B/A with existing 0644 params, no build.
3. **The 240 MHz mirror arm is information, not a step toward shipping 400.**
   400 MHz runs the shared cache domain 25% over spec; the failure mode is
   silent PSRAM corruption. 360 is the realistic ceiling.
4. **T1.9 (storage) is demoted.** `MMC_CAP_DONE_COMPLETE` is set by no
   in-tree driver and silently disables CMD13 write-error detection; C60 is a
   week for +1.2%. Run the free SD-stat census; otherwise leave storage alone.

## Rules that hold throughout

- Nothing below the lottery ships on its own fps number. Bundle, and judge on
  pingpong medians, `/proc/interrupts` rates and h1s sample shares; fps only as
  a multi-boot median at the end.
- Fresh boot per arm where the effect is claimed on fps; same-boot A/B/A only
  with the A-to-A gap reported as the error bar (dead-end #19).
- Nothing touches the board while a measurement is in flight. Every board
  test <= 10 minutes per result.
- App code, app placement (SD), Bluetooth and Wi-Fi are untouchable.
- **After a platform change ships** (not per experiment), re-check that
  Doom and the desktop did not regress: `scripts/board/timedemo.sh <name> 2
  fullscreen` (prboom, detached, no polling) and `scripts/board/gate.py
  --reset` (contract + smoke + the sdl1 canary against gate-baseline.json),
  plus an xcalc launch and screenshot, and OpenTyrian (no timedemo: ~20 s of
  the title animation, lvdesk's SIGUSR1 frame-gap histogram, a screenshot).
  Improvements there would be welcome; no regression is the requirement.
  Record the numbers here even when nothing moved. (User, 2026-09-23.)
  Baselines to beat or hold: Doom fullscreen 39.1 fps (2026-09-21, late
  present); desktop canary sdl1-indexed 14.725 ms mean (gate-baseline.json,
  2026-09-20).

## Phase 3b - code size IS time (added 2026-09-23 after the counters)

The counters put the kernel path at 91% fetch-stalled and Phase 0's 9% text
cut returned 9.4% on pingpong: on this platform bytes fetched from flash are
time, and the review priced every code-size item by "samples on those
instructions", which undercounts ~4x. Re-rank accordingly, cheapest first:

- [x] **`-msave-restore` for the kernel** - BUILT (#341, -188 kB) AND
      MEASURED WORSE: pingpong 491 -> 529 us, Quake 19.1 -> 17.7. Not shipped;

      and always I-cache-resident. One build, pp-boots 3 boots, Quake 2 boots.
- [x] **Zcmp/Zcb (C38) probe, EFFECT-CHECKED: both execute on both harts in

## Phase 3c - the flash headroom (added 2026-09-23, user)

622 kB free in the linux partition and ~780 kB across the two userspace XIP
images. Flash is the slow tier for EXECUTING the kernel, but for anything
that would otherwise page from SD it is the fast one: a cramfs page is a
cache fill, an SD page is a 2.5 ms request. So the headroom is worth
something exactly where platform code still lives on the card.

- [x] **XIP census** (scripts/board/xip-census.sh, 2026-09-23). Truly on the
      card: bluetoothd (1.18 MB, RSS 0, idle - pages only on pairing/connect/
      discovery), udevd (241 kB, RSS 0), and PID 1. busybox and lvdesk are
      XIP (00:2b, 00:1e). **PID 1 runs the ext4 root's DYNAMIC busybox with
      its own libc.so from SD (started before the overlays stacked) and holds
      ~476 kB resident: 256 kB busybox + 220 kB libc, duplicating code every
      other process gets from XIP at zero RSS.** Static busybox on the ext4
      root is the fix - a cheap half-megabyte. Original item text follows.
- [ ] (original) **XIP census.** For every running process: where its executable and
      each mapped library live (XIP overlay vs ext4) and how much of each is
      resident file cache. 30 s of board time. Known suspect: busybox is
      static, ~1 MB, and `/bin` is not overlaid, so every exec re-faults it
      from SD after Quake has evicted it. NOT a suspect: bluetoothd, which is
      idle during A2DP (our s31-a2dp streams) and pages only on pairing,
      connect and discovery. Move what the census names; apps stay on SD.
- [x] **KALLSYMS**: SHIPPED #354 (Quake 19.5, gate 22/22, no RAM cost).
      Original text: +590 kB (not the ~200 kB estimated). Against the 623 kB
      headroom it left 33 kB, so I closed it - wrongly priced, the user
      points out: against the Zcmp kernel's 1,097 kB it fits with ~500 kB
      spare. If #353 holds, KALLSYMS=1 joins the shipped config.
- [x] **Selective -O2 on hot flash objects** (the kernel is -Os): CLOSED
      2026-09-23, #355 via `O2OBJS=`: +32.8 kB, pingpong +2.7%, Quake
      19.5 vs 19.5. Bytes are time; -O2 buys nothing back.
- Keep ~300 kB of the kernel partition as permanent slack; every version
  bump has grown the image. Do not repartition until the userspace images
  are full. No swap in flash: NOR program/erase is slow and wear-limited.

## Phase 5 - only if Phase 2 was steep (it was: slope 0.72)

The vendor clock code (rtc_clk.c rtc_clk_cpu_freq_to_cpll_mhz) fixes CPLL at
320 and derives CPU/MEM/SYS/APB by dividers under the constraints MEM <= 160,
SYS <= 106.67, APB <= 53.33. The 240 mirror arm therefore moved CPU AND MEM
(120) together, so its 0.72 slope cannot say which one Quake follows - and
that is exactly the 360 question, because 360 means MEM 180 (12.5% over the
ceiling) or MEM 120 (mem_div 3, a 25% memory under-clock).

- [x] **CPU 160 / MEM 160 arm - NOT AVAILABLE.** The S31 sdkconfig offers
      only 240 and 320; a build attempt edited the DTS and OpenSBI but not
      the loader (mismatched trio, #346, discarded). Separating the CPU and
      memory slopes would need a vendor HAL patch; not worth it, because 360
      moves both by the same ratio as the mirror arm did, so the 0.72 slope
      applies directly (-> ~21 fps). The only open question is memory-domain
      integrity at MEM 180, which no arm answers - only a pattern test and a
      soak (rootfs/memtest.c).
- [ ] **360 MHz arm IN FLIGHT** (trio in images/oc360: loader with the
      in-app switch in bootloader/main/s31_oc.h, OpenSBI and kernel #348 at
      the 360 timebase; vendor clock code patched for 360 inside the
      container for that build only - fb_div 9, dividers mem 2 / sys 4 /
      apb 2, so MEM 180, SYS 90, APB 45). Guardrails in order: host/board
      clock ratio must read TRUE; memtest 2 MB x 3 passes on each CPU with
      swap OFF (the SD sees no writes while the memory domain is unproven);
      quick gate; only then two quiet Quake boots; then the 320 trio back
      via flash-trio.sh and its own ratio test. memtest at 320: 0 mismatches.
- [x] **360 arm: RADIOS OK** (user rule). 360 run 1/2: wget 615 / 538 KB/s,
      ping loss 0% / 3%, avg 10.7 / 12.1 ms, -62/-63 dBm, BT powers on and
      scans; 320 before/after: 628 / 701 KB/s, 3% / 3%, 10.5 / 8.5 ms. No
      association loss, no BT failure; throughput ~10% lower on n=2, inside
      the band, to be re-read in a soak.
- [ ] **Ship decision for 360 - the user's call.** Evidence: clock proven
      every flash (0.988-0.998), memtest clean twice on both CPUs (2 MB x
      3-4, once after a Quake run with swap on), gate 22/22, Quake 20.9 /
      19.2 / 20.0 / 19.4 (median 19.7, +3-4%; two of four boots >= 20),
      radios as above. Against: the memory domain runs 180 MHz on a vendor
      ceiling of 160, permanently, for +3-4% - and the only board. If it
      ships: s31_oc.h -> 360 permanently, the vendor patch applied by the
      Makefile on every loader build (the container IDF is pristine per
      run), DTS and OpenSBI timebases to 360, and a real soak first (an hour
      at 360: memtest loops, Doom, the desktop, radios).
- [ ] 400 only if 360 ships and soaks clean; it runs the memory domain 25%
      over, and the 360 result says the gain would be ~+5%, not the +18%
      the mirror slope promised.

- [ ] 360 MHz with a multi-boot soak. 400 only with a corruption check over
      PSRAM under load, and only if 360 delivers.

3. SEMANTICS - EXACTLY libgcc's, AND WHAT libgcc ITSELF DOES
------------------------------------------------------------
The reference is this target's libgcc (soft-fp, riscv sfp-machine.h). Its
disassembly shows each routine reading frm at entry (frrm) and accruing
flags with csrs fflags. v2 splits the work in two.

  Fast paths:
    - normal operands and a normal result;
    - zero operands (x*0, x+0, 0/y);
    - powers of two (mul, div);
    - int/float-derived operands whose low word is zero (mul);
    - frm == RNE.
    These are computed in place and raise exactly what soft-fp raises
    there: NX when inexact. Overflow and underflow never happen on a fast
    path, because the exponent range checks exclude them.
  Everything else:
    - NaN, inf, subnormals, 0*inf;
    - results that leave the normal range;
    - frm != RNE.
    These tail-call libgcc's own routine with the argument registers
    untouched, so they are libgcc by construction rather than by imitation.

frm:
  Honoured. Any mode other than RNE goes to libgcc, which rounds exactly as
  libgcc does.

fflags:
  Reproduced bit for bit (checked on every operand set, from random initial
  flags). Each routine reads fcsr ONCE, getting frm and the accrued flags
  together, and writes NX only when it is not already set.
    Why: a CSR access costs 25-30 ns on this core (section 5).
    Sole difference from libgcc: if a signal handler clears NX between that
    read and the routine's end, libgcc would set NX again and v2 does not.
  fixdfsi and fixunsdfsi ignore frm (they truncate), read no CSR, and write
  NX when the result is inexact.

NaN:
  libgcc on this target returns the canonical quiet NaN 0x7ff8000000000000
  for arithmetic (0 non-canonical NaN results over 80 M mul/add/sub/div
sets). But:
  extendsfdf2 KEEPS the float NaN's payload and sign, and fixdfsi saturates
  a NaN by its sign bit. v2 gives NaNs to libgcc, so it matches all of this
  by construction.

Where libgcc is not IEEE (from the QEMU D-extension oracle; v2 matches
libgcc, deliberately):
  - frm = RMM (4): libgcc does not implement round-to-max-magnitude and
    truncates instead. It differs from IEEE on about 8% of mul/add/sub/
    div/trunc operand sets in that mode. RNE, RTZ, RDN and RUP agree with
    the oracle on every set, flags included.
  - fixdfsi(NaN) gives INT_MIN for a negative NaN; hardware gives INT_MAX.
    fixunsdfsi(NaN or negative) gives 0; hardware gives UINT_MAX for NaN.
    Both raise NV.
  - extendsfdf2(NaN) keeps the payload; hardware canonicalises.

Frozen variants, measured, not proposed:
  FFLAGS=0   frm honoured, NX not raised on fast paths
  FENV=0     no CSR access at all
Results under RNE are identical in both (checked). They exist only to price
the fenv work.

6. THE INTERCEPTION: libs31fp.so (preload3.c)
---------------------------------------------
What it does:
  - Finds libgcc's statically linked double routines in the MAIN
    EXECUTABLE's text.
  - Overwrites each entry with `auipc t0 / jalr x0, t0` to the v2 routine.
  - The page is a private copy-on-write copy; the file is untouched.

Matching - no match, no patch:
  - Full bodies, not prefixes. 13 of the 14 libgcc members contain only
    intra-routine branches, so their linked bodies are the member's .text
    byte for byte. __divdf3 has one PC-relative data reference: those two
    instruction words are masked, and if the linker relaxed it the length
    differs and nothing matches.
  - A prefix match would have been WRONG. __gedf2 and __ledf2 are identical
    for their first 64 bytes; they differ only in the unordered return
    value (-2 vs 2). The 2026-09-20 preload's 64-byte scheme would have
    patched __ledf2 to the ge routine. It never included the comparisons,
    so it was not affected.
  - mksig3.py now asserts that no two bodies are equal.
  - Guards: it never patches its own renamed reference copies or its own
    signature tables. The static QEMU test caught the second, because
    rodata can share the executable segment.

Patch sequence: the RAMTEXT one (gl/.../s31_ramtext.c). Here the I-cache
does not snoop the D-cache and fence.i does not write the D-cache back; the
kernel's exec-PTE hook does. So:
  1. one mprotect to RW (never W+X);
  2. every write, as halfwords (RVC alignment);
  3. one mprotect back to RX, which gives D-cache writeback and I-cache
     invalidate for the new COW frames;
  4. the fence.i syscall and a fence.i.
Nothing is written after step 3. The main executable's code runs only after
all shared-library constructors, so no CPU-written instruction can execute
before step 3. If the RW mprotect fails, nothing is patched.

Launch cost:
  - Only the main executable is scanned.
  - One pass, 2-byte aligned, through a 4096-bit filter on the first
    halfword.
  - Per-binary cache in $S31FP_CACHE, default /var/lib/s31fp. It is ext4:
    /var/cache on this board is a symlink to the tmpfs /tmp. The key is
    dev/inode/size/mtime (statx of /proc/self/exe). The entry holds the
    offsets, or nothing for a binary with no helpers. It is written
    tmp+rename, and every body is re-verified on a hit.
  - No libc: raw system calls and a single import (environ). Its 72
    relocations are all RELATIVE.
  - About 10 system calls in the constructor: auxv open/read/close, statx,
    cache open/read/close, 2x mprotect, fence.i. On this board syscalls,
    not scanning, are the remaining cost.

  Measured (board-b4.txt, two rounds), ms per launch over 20 launches each,
  busybox env in every arm. The plain column is absolute; the others are the
  change from plain:

    app                      plain   old preload  loaded, off   scan    cache
    oplbench-dyn              48.2   +159.8        +4.8         +12.8   +27.8*
    sdltone1 (libSDL)         67.8   +241.0        -3.2          +3.8    +6.0
    amixer -v                 83.5   +392.0        +0.0          +5.5   +10.8
    aplay --version           90.5   +362.0        -2.0          +9.2   +13.2
    bluetoothctl --version   113.8   +392.0       +12.8         +28.0   +20.8

  * that round included a poll of mine; the other round read +13.

  - "loaded, off" (S31FP=0) is the dynamic loader mapping the library and
    nothing else.
  - The noise is about +-8 ms; with that, scan and cache are the same for
    these small programs. A cache hit pays statx plus an open/read/close,
    which is about what scanning a small text costs. The cache pays off on
    big texts (below).
  - On this board a syscall, not the scan, is the unit of cost.
  - Patched per program: oplbench 10, sdltone1 9, amixer 7, aplay 8,
    bluetoothctl 2, glxgears 10, OpenTyrian 12.

  Scan cost of big texts, as a file (scanbench, the same filter; board):
    sdlquake   435 KB   12.1 ms   27.7 ns/B   11 routines
    prboom     693 KB   20.4 ms   29.4 ns/B    6 routines
  That cost is paid on the first launch only; later launches are cache
  hits. OpenTyrian's cache entry survived a reboot and was hit on the next
  fresh boot.

Memory:
  - 25 KB of shared text/rodata. It belongs in XIP image 1, where it costs
    zero RSS.
  - One private 4 KB page per process (1.3 KB of data/bss/GOT).
  - For a patched program: the COW'd text pages holding the patched entries,
    typically 2-3 pages.
  - OpenTyrian measured: VmRSS 2100/2052 kB with the preload against 2016/2044 kB without, and Private_Dirty 1484/1488 against 1468/1468 kB, i.e. +16-20 kB

Trampoline cost: the extra auipc+jalr on every call costs about 3.1 us per sample (16%) on
the title song against the statically linked v2 (18.89 static vs 22.00
through the preload, same helpers).

Not covered: static binaries, dlopen()ed objects, and shared libraries' own
copies (musl's libc.so, libSDL and the rest keep theirs).

Missing library: if LD_PRELOAD names a missing file, musl still starts the
program. Measured: the program ran and printed its usage.

8. THE STOCK GAME, AND THE REGRESSION SET (fresh boots)
-------------------------------------------------------
OpenTyrian = /root/oty/usr/bin/opentyrian, the binary the lvdesk menu
starts. At its title, music playing, fresh boot, measured over a 20 s window
with nothing polling. Preload arms: LD_PRELOAD for that launch only.

  arm                 boot   xruns/s   audio thread CPU   process CPU
  stock               B      14.62     94.9%              120.1%
  stock               D      14.20     94.8%              120.3%
  v2 preload (scan)   A      26.59     92.4%              118.1%
  v2 preload (cache)  C      26.56     92.4%              117.9%

The preload patched 12 routines in the game. The four boots repeat to within
0.4 xruns/s, but the two arms clearly differ, and in the WRONG direction on
this metric.
  - The audio thread is saturated in both arms (92-95% of a CPU), so the
    music is still not real-time.
  - The synthesis alone needs 0.97 cores through the preload (oplbench),
    and the callback does more than synthesis.
  - The earlier study saw the same pattern with the old s31fp (7.1 -> 12.7
    xruns/s) and read it as a faster synth making more restart cycles.
    That is plausible, but not established here. I did not listen, and
    xruns/s alone cannot say which arm sounds better.
Verdict: v2 through the preload does NOT make OpenTyrian's title real-time.
An ear check is needed before claiming it is better or worse.

Memory, OpenTyrian with the preload: +16-20 kB private dirty (the COW'd text
pages plus the library's data page).

Regression, quiet (DAC 110 during the run, restored to 143); one fresh boot
per arm, run after the OpenTyrian arm on the same boot:

  arm          boot   glxgears (3 x 5 s)       prboom timedemo (-window)   sdlquake timedemo

Only one plain boot for prboom and sdlquake, so the spread is thin. Another

9. OPEN / NEXT
--------------
- Not shipped. The system-wide delivery is written down in delivery.diff
  (profile + lvdesk + XIP image 1 + /var/lib/s31fp), awaiting the owner.
- The trampoline costs 16% of the title-song gain (22.00 via the preload
  against 18.89 static). Removing it means copying the v2 routine into the
  patched body, with its PC-relative calls into s31lg_* retargeted. That is
  the same write-then-RX step as RAMTEXT, with more code written. It is
  worth ~3 us per sample for OpenTyrian and nothing for most programs.
- fenv: fcsr-once with NX-only-if-unset is already applied. The remaining
  CSR read costs ~1 us per sample on the title. Dropping NX on fast paths
  (frm-only) saves another 0.95 us, at the price of a stated deviation.
  Owner's call.
- Even with every lever (v2n static, 16.87 us = 0.74 cores), OpenTyrian's
  title leaves the audio thread little margin, and song 5 needs 1.1 cores.
  The earlier study's conclusion stands for the loud songs.
- Exec cost: about 10 syscalls in the constructor. Reading AT_PHDR through
  dl_iterate_phdr instead of /proc/self/auxv (3 syscalls), and keying the
  cache on an in-memory fingerprint verified by the body check instead of
  statx (1), would take a further few ms off every launch.
- Test binaries remain in /root/afp2 on the card, along with the test cache
  /root/afp2/cache. Nothing outside /root/afp2 was changed.


10. COPY-IN-PLACE, FRAME COLOURING, AND WHAT SHIPPED (2026-09-27, later)
-----------------------------------------------------------------------
Copy-in-place (S31FP_COPY=1): the v2 routine is copied over libgcc's own
body in the program instead of jumping to it.
  - 13 of 14 routines: all but divdf3, which is compiled C.
  - gedf2/ledf2 are 200 bytes against libgcc's 184, so only their
    non-negative fast compare is copied; other cases jump back to the full
    routine in the library.
  - v2.S is built without linker relaxation, and every fallback tail call
    is an explicit auipc/jalr pair recorded in section s31fix, re-encoded
    for the copy's address. build-preload3.sh fails unless those pairs are
    the only relocations.
  - QEMU: 0 mismatches over 5 M sets per helper through the copies, and
    4,783 instructions per sample for the title song, the same as static v2
    (trampoline 4,973).
  - Board: 14/14 two-process dumps identical (unpatched, copy, trampoline)
    and 280/280 in the hammer (board-b5.txt).

Title song, CPU0, us per sample:
  static v2                       18.2-18.4
  copy, uncoloured                19.4-20.5 in most runs, but 22.6-31.1 in
                                  about 1 run in 4-6 (board-b6/b7.txt)
  copy, colour-placed             19.9-20.6 in 26/26 runs (0.88 core;
                                  board-b8/b10.txt)
  trampoline                      21.3-22.1
CPU1 (the lent hart) is 20-25% slower for EVERY arm, static v2 and plain
libgcc included (board-b9.txt), so that is a property of the hart, not of
the preload.

The lottery is the physically indexed I-cache (32 kB, 2-way, 16 kB per way;
frame bits 12-13 pick the colour). The write COW's each patched text page
into a fresh frame of random colour. In board-b7.txt the slow runs are
exactly those where two or three of the patched pages drew colour 0.
The fix is to give each patched page a frame of its ORIGINAL page-cache
frame's colour:
  1. take frames from a small populated anonymous pool, 4 pages at a time
     (colours read from pagemap, root only);
  2. copy the page's original bytes into the chosen frame and mremap it
     over the text page BEFORE any write (it arrives RW, never executable);
  3. then the usual writes, the single RX mprotect (the cache flush) and
     fence.i.
This is the RAMTEXT tier-6 technique. It costs about +6 ms per launch, and
the whole preload costs about +20 ms per launch with copy+colour.

WHY COPY-IN-PLACE DID NOT SHIP: one prboom timedemo, run under
copy+colour after the OpenTyrian arm on a fresh boot, died of SIGSEGV at
level load, then hung in I_ShutdownSound. That was 1 of 4 prboom runs under
copy; the 3 others (25 s each, past level load, with segvtrap) were clean,
and I could not reproduce it or find a cause. Every trampoline prboom run
completed. So the shipped library defaults to the trampoline, and copy is
opt-in (S31FP_COPY=1; colouring then applies automatically). The cost of
that choice is ~1.3 us per sample on OpenTyrian's title.
